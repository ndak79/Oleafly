## 1. Review oracle

The plan passes only when all of the following are true in one final full
closed-coverage review after the last repair:

1. It stays inside the approved Scientific AI IDE scope and the twelve named
   slices; T0.2 does not pretend to deliver later LaTeX, research, AI, Git, or
   publishing slices.
2. Every TExFlow-owned executable behavior, parser, fixture, oracle, controller,
   worker, and QA client is planned in Zig. The only shell exception is the
   irreducible CI bootstrap before the verified Zig executable exists.
3. Each architecture boundary has an implementable ownership, lifetime,
   resource, error, cancellation, fallback, and kill-switch contract.
4. Every one of A01-A19 has direct evidence and an unambiguous owner; no
   `as applicable`, skipped, simulated, pooled, retried-away, or screenshot-only
   evidence can silently close a mandatory row.
5. The task order is executable: a task cannot require an authoritative harness,
   ABI, sandbox, source artifact, or oracle that is planned only in a later task.
6. Performance claims use frozen physical hardware and OS/profile strata,
   preregistered samples, honest cold/warm definitions, complete raw data, and
   fail-closed measurement parsers.
7. Security and supply-chain claims distinguish integrity, provenance,
   reproducibility, sandboxing, signing, and release qualification.
8. Every Medium/High/Critical finding is repaired in the plan, then resets the
   streak to `0/1`. Low findings are fixed or explicitly accepted and cannot
   accumulate into a systemic Medium gap.

9. “Zero named capabilities” never masquerades as zero ambient authority:
   product workers prove LPAC/AAP-opt-out token state before resume, disclose
   and trace the `ALL RESTRICTED APPLICATION PACKAGES` residual baseline,
   distinguish AAP/ARAP/exact-role grants with canaries, and prove full corpus
   compatibility without a regular-AppContainer or restricted-token fallback.
10. The exact `TExFlow.exe`, `TExFlow.PdfWorker.exe`, and
    `TExFlow.ScienceWorker.exe` split is real rather than cosmetic: recursive
    imports/live modules, ACLs, names, and the frozen pre-start mitigation
    profile are independently proved before worker input admission. New product
    identity uses exact `TExFlow` casing, role-specific PE resources, and
    lowercase machine namespace `texflow`; legal publisher data is not invented
    and repository lineage appears in shipping only where an audited legal
    notice requires it, never as product/publisher identity.
11. LPAC IPC remains internally executable: its pipe DACL supplies both exact
   normal and package principals without broad/create-instance rights; a
   same-logon transport open is rejected before application data by the authenticated
    transcript; and worker parent proof never requires access to denied UI bytes.
12. Unicode, canonical storage, and search behavior are one versioned contract: Unicode-17 data and
    UAX profiles, UIA unit meanings, tokenizer normalization, accent semantics,
    single-copy project-scoped content chunks and typed event/projection
    references under the ledger row/root limits, contentless-delete/UUID-map
   storage, bounded entity transport, control/database thread ownership,
   staging activation, short query-only ledger
    snapshots with finalize-before-tokenize/revision recheck, descriptor-free worker
   results, broker proof before display, the exact
   whitespace/control/elision/untitled presentation grammar with layout-only BiDi isolation, exact
   epistemic and eligibility semantics, `H`-based first-use/warm endpoints, and
   complete-root footprint agree across tasks and acceptance.

An HTML render may receive one publication smoke test if emitted, but neither

## 2. Review method

The review uses five independent lenses rather than repeated paraphrases:

- **Scope and traceability:** compare the approved spec, roadmap accounting,
  A01-A19, task ownership, build steps, commit gates, and T1 admission rule.
- **Architecture and failure analysis:** walk UI, editor, worker, IPC, PDF,
  SQLite, presentation, accessibility, capture, and measurement lifetimes in
  both success and hostile/failure order.
- **Decision challenge:** compare the chosen stack with mainstream and
  specialist alternatives, inspect failure modes, and rerun sensitivity checks.
- **Implementation executability:** verify prerequisite order, named files,
  test-first steps, deterministic fixtures, negative tests, timeouts, CI, and
  evidence retention.
- **Fresh factual audit:** recheck primary sources, exact versions, link
  reachability, repository baseline, and remote CI state without treating source
  availability as proof of runtime behavior.
